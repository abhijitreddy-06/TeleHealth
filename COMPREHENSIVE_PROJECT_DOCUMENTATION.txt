3.2 KEY OPTIMIZATIONS
----------------------

A. DATABASE LAYER OPTIMIZATIONS:
──────────────────────────────
1. Connection Pooling:
   - Max 3 simultaneous connections
   - 30-second idle timeout to free unused connections
   - 10-second connection timeout for quick failure detection
   - Health monitoring via getPoolHealth() every 30 seconds

2. Query Optimization:
   - Partial indexes on frequently filtered columns (active status, ratings)
   - Full-text search indexes (GIN) on product names/descriptions
   - Covering indexes where possible (category_id, user_id lookups)
   - Advisory locks (PostgreSQL) for serializing conflicting appointments

3. Transaction Management:
   - ACID compliance with explicit BEGIN/COMMIT/ROLLBACK
   - Transaction isolation levels prevent race conditions
   - Automatic cleanup of expired tokens every 60 minutes

B. CACHING LAYER OPTIMIZATIONS:
────────────────────────────────
1. Doctor List Cache:
   - Key: "doctors:available"
   - TTL: 300 seconds (5 minutes)
   - Invalidated on: appointment completion, schedule update
   - Reduces database load during peak booking hours

2. Token Management:
   - Refresh tokens stored in PostgreSQL with revocation tracking
   - Automatic cleanup of expired tokens older than 30 days
   - Prevents token reuse after logout/revocation

3. Redis Locks (Slot Reservation):
   - Key: `locks:${doctorId}:${date}:${time}:${userId}:${lockToken}`
   - TTL: 15 minutes (time for patient to complete booking)
   - Prevents overbooking during race conditions

C. API RESPONSE OPTIMIZATION:
──────────────────────────────
1. Compression:
   - Gzip compression enabled for all text responses
   - Typical reduction: ~70% of payload size
   - Automatic for responses >1KB

2. Pagination:
   - Default page size: 10 items
   - Offset-based pagination for compatibility
   - Indexes on created_at DESC for chronological queries

3. Response Normalization:
   - Consistent JSON contract across all endpoints
  - Format: { success: boolean, message: string, data: any }
   - Automatic status code inference
  - Exception: binary download endpoints (PDF/files) return streamed/buffer data

D. CONCURRENCY CONTROL (Race Condition Protection):
──────────────────────────────────────────────────
Three-layer protection system prevents double-booking:

LAYER 1 - Redis Lock (Client-side):
  - Patient requests available slots → server locks with Redis
  - Lock token valid for 15 minutes
  - If lock expires, patient must re-select slot

LAYER 2 - PostgreSQL Advisory Lock (Server-side):
  - Serializes transactions on same (doctorId, date)
  - Ensures only one booking can execute at a time
  - Timeout after 5 seconds (postgres default)

LAYER 3 - Unique Constraint Index:
  - UNIQUE (doctor_id, appointment_date, appointment_time, status != 'cancelled')
  - Database-level enforcement
  - Catches edge cases where Layers 1-2 fail

Result: Guaranteed no double-booking even under high concurrency (tested up to 100 simultaneous requests)

E. REAL-TIME OPTIMIZATION:
──────────────────────────
1. Socket.IO Architecture:
   - Redis pub/sub adapter enables clustering
   - Each connection stored in memory (lightweight)
   - Graceful reconnection with 30-second grace period

2. WebRTC Optimization:
   - Codec negotiation for optimal quality/bandwidth
   - ICE restart support for network changes
   - STUN/TURN configuration for NAT traversal

3. Event Batching:
   - Mute/camera state updates debounced client-side
   - Dashboard stats updated once per second (not per message)

4. SECURITY IMPLEMENTATION
================================================================================

4.1 AUTHENTICATION & AUTHORIZATION
-----------------------------------

A. USER AUTHENTICATION:
   Mechanism: JWT (JSON Web Token) with refresh token rotation
   
   Login Flow:
   1. POST /api/auth/patient/login with phone + password
   2. Backend verifies credentials against bcrypt hash (10 salt rounds)
   3. Generates access token (15-minute expiry) + refresh token (7-day expiry)
   4. Tokens set as httpOnly cookies with Secure + SameSite flags
   5. Returns accessToken in response for AJAX requests
   
   Token Rotation:
   - Access token expires after 15 minutes
   - Refresh token stored in refresh_tokens table with expiration tracking
   - On token refresh: revoke old token, issue new pair
   - Old tokens cannot be reused (tracked in revoked column)
   - Automatic cleanup of expired tokens older than 30 days

B. PASSWORD SECURITY:
   - Bcrypt hashing with 10 salt rounds
   - Password validation: min 6 chars, at least 1 uppercase, 1 digit
   - Password confirmation required on signup
   - Passwords never logged or transmitted in plain text

C. AUTHORIZATION (Role-Based Access Control):
   Three roles: 'user' (patient), 'doctor', 'admin'
   
   Example Protected Routes:
   - POST /patient/profile (authorize 'user')
   - POST /api/appointments/:id/complete (authorize 'doctor')
   - GET /api/admin/stats (authorize 'admin')
   - DELETE /api/pharmacy/products/:id (authorize 'admin')

D. COOKIE SECURITY:
   Access Token Cookie:
   - httpOnly: true (prevents XSS theft via document.cookie)
   - secure: true (only over HTTPS in production)
   - sameSite: 'None' (for cross-site requests) or 'Lax' (same-site)
   - maxAge: 15 minutes (900,000 ms)
   
   Refresh Token Cookie:
   - httpOnly: true
   - secure: true
   - sameSite: 'None' or 'Lax'
   - maxAge: 7 days (604,800,000 ms)

4.2 NETWORK SECURITY
--------------------

A. HELMET SECURITY HEADERS:
   - Content-Security-Policy (CSP): Restricts resource loading origins
   - X-Frame-Options: DENY (prevents clickjacking)
   - X-Content-Type-Options: nosniff (prevents MIME sniffing)
   - Strict-Transport-Security: max-age=31536000 (HSTS)
   - X-XSS-Protection: Removed in modern browsers (CSP sufficient)

B. CORS CONFIGURATION:
   Production:
   - Allowed origins: Explicitly listed (FRONTEND_URL env var)
   - Methods: GET, POST, PUT, DELETE, PATCH
   - Headers: Content-Type, Authorization, X-Requested-With
   - Credentials: true (allow cookies)
   - Max age: 600 seconds
   
   Development:
   - Localhost allowed for testing
   - Credentials: true

C. RATE LIMITING:
   Authentication Endpoints:
   - 15 requests per 15 minutes per IP
   - Applies to: signup, login, refresh token
   - Uses trust proxy (handles reverse proxies correctly)
   
4.3 INPUT VALIDATION & SANITIZATION
------------------------------------

A. SCHEMA VALIDATION (Zod):
   All request bodies validated against schemas:
   
   Example - Appointment Booking:
   ```
   bookAppointmentSchema = {
     doctor_id: z.number().int().positive(),
     appointment_date: z.string().date().refine(d => d >= today),
     appointment_time: z.string().time(),
     symptoms: z.string().optional()
   }
   ```
   Validation middleware rejects invalid payloads with 400 errors

B. HTML ESCAPING:
   All user input sanitized before storage/display:
   - Function: escapeHtml(input)
   - Encodes: <, >, &, ", '
   - Prevents XSS attacks in medical records

C. FILE UPLOAD RESTRICTIONS:
   Multer configuration:
   - Allowed MIME types: image/jpeg, image/png
   - Max file size: 5MB
   - Filename sanitization (removes special characters)
   - Storage: Supabase cloud storage (encrypted at rest)

4.4 DATA PROTECTION
-------------------

A. ENCRYPTION AT REST:
   - Supabase: AWS S3 with server-side encryption
   - PostgreSQL: Can be configured with pgcrypto extension
   - Redis: In-memory, no encryption needed (transient data)

B. ENCRYPTION IN TRANSIT:
   - HTTPS/TLS required in production (enforced by Secure cookie flag)
   - WebSocket secured with WSS (wss://) in production
   - Certificate validation enforced

C. SENSITIVE DATA HANDLING:
   - Passwords: Never logged, hashed immediately
   - Tokens: Stored in httpOnly cookies (not localStorage)
   - Medical records: Encrypted before upload to Supabase
   - Prescriptions: PDF generated server-side, no customer data stored

4.5 AUDIT & MONITORING
----------------------

A. LOGGING:
   Winston logs capture:
   - Authentication attempts (success/failure)
   - Authorization failures (403 responses)
   - Database errors (with sanitization)
   - File uploads (name, size, mime type)
   - API errors (method, path, status code)
   
   Log levels:
   - error: Application errors, exceptions
   - warn: Authentication/authorization failures, transient errors
   - info: Service startup, significant events
   - debug: (in development only)

B. SESSION TRACKING:
   - Refresh tokens table logs: user_id, role, created_at, expires_at, revoked
   - Allows historical audit of who had valid sessions

C. SOCKET.IO LOGGING:
   - Connection/disconnection events logged
   - Failed authentication logged (socket level)
   - Room transitions traced (join-room, signal exchange)

5. DATABASE ARCHITECTURE (SCHEMA & DESIGN)
================================================================================

5.1 CORE IDENTITY & AUTHENTICATION
-----------------------------------

TABLE: users
Purpose: Central user registry (patients, doctors, admins)

Columns:
- id: SERIAL PRIMARY KEY
- phone: VARCHAR(20) UNIQUE NOT NULL (login identifier)
- password: VARCHAR(255) NOT NULL (bcrypt hashed)
- role: VARCHAR(20) NOT NULL ('user'|'doctor'|'admin')
- created_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- phone (unique constraint for login lookup)

Relationships:
- 1:1 with user_profile (patients)
- 1:1 with doc_profile (doctors)
- 1:many with refresh_tokens
- 1:many with appointments
- 1:many with ai_prechecks
- 1:many with pharmacy_orders

TABLE: refresh_tokens
Purpose: Track valid refresh tokens and enable revocation

Columns:
- id: SERIAL PRIMARY KEY
- user_id: INT NOT NULL REFERENCES users(id)
- role: VARCHAR(20) NOT NULL (cached from users.role for performance)
- token: TEXT UNIQUE NOT NULL (JWT token string)
- expires_at: TIMESTAMPTZ NOT NULL
- revoked: BOOLEAN DEFAULT FALSE
- revoked_at: TIMESTAMPTZ (when token was revoked)
- created_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (user_id) for quick token lookup on login/refresh
- (expires_at) for cleanup queries

Relationships:
- many:1 with users

Features:
- Automatic cleanup of expired tokens older than 30 days
- Supports token revocation on logout
- Prevents token reuse after logout

5.2 USER PROFILES
-----------------

TABLE: user_profile
Purpose: Patient profile information (1:1 with users role='user')

Columns:
- id: SERIAL PRIMARY KEY
- user_id: INT UNIQUE NOT NULL REFERENCES users(id) ON DELETE CASCADE
- full_name: VARCHAR(255) NOT NULL
- gender: VARCHAR(50)
- custom_gender: VARCHAR(100) (other gender option)
- date_of_birth: DATE
- weight_kg: NUMERIC(5,2)
- height_cm: NUMERIC(5,1)
- blood_group: VARCHAR(10) ('O+', 'AB-', etc.)
- allergies: TEXT (comma-separated list)
- created_at: TIMESTAMPTZ DEFAULT now()
- updated_at: TIMESTAMPTZ DEFAULT now() (auto-updated by trigger)

Index:
- user_id (unique for 1:1 relationship)

Relationships:
- 1:1 with users

TABLE: doc_profile
Purpose: Doctor profile information (1:1 with users role='doctor')

Columns:
- id: SERIAL PRIMARY KEY
- doc_id: INT UNIQUE NOT NULL REFERENCES users(id) ON DELETE CASCADE
- full_name: VARCHAR(255) NOT NULL
- specialization: VARCHAR(255) (e.g., 'Cardiology', 'Pediatrics')
- experience_years: INT
- qualification: VARCHAR(500) (e.g., 'MBBS, MD (Cardiology)')
- hospital_name: VARCHAR(255)
- bio: TEXT
- created_at: TIMESTAMPTZ DEFAULT now()
- updated_at: TIMESTAMPTZ DEFAULT now()

Index:
- doc_id (unique for 1:1 relationship)

Relationships:
- 1:1 with users

5.3 APPOINTMENTS
----------------

TABLE: appointments
Purpose: Core appointment records with 3-layer booking protection

Columns:
- id: SERIAL PRIMARY KEY
- user_id: INT NOT NULL REFERENCES users(id)
- doctor_id: INT NOT NULL REFERENCES users(id)
- appointment_date: DATE NOT NULL
- appointment_time: TIME NOT NULL
- room_id: VARCHAR(100) UNIQUE NOT NULL (UUID for WebRTC room)
- symptoms: TEXT (patient's initial symptoms)
- status: VARCHAR(50) NOT NULL DEFAULT 'scheduled'
  Values: 'scheduled'|'approved'|'started'|'completed'|'cancelled'
- cancel_reason: TEXT (if cancelled by patient or doctor)
- cancelled_by: VARCHAR(20) ('user'|'doctor'|'admin')
- cancelled_at: TIMESTAMPTZ
- created_at: TIMESTAMPTZ DEFAULT now()
- updated_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (doctor_id, appointment_date, appointment_time, status) PARTIAL WHERE status != 'cancelled'
  (UNIQUE constraint - prevents double-booking)
- (user_id, status) for patient's active appointments
- (doctor_id, appointment_date) for doctor's schedule
- (created_at DESC) for chronological queries

Relationships:
- many:1 with users (user_id - patient)
- many:1 with users (doctor_id - doctor)
- 1:1 with prescriptions
- 1:many with call_sessions (WebRTC recordings)

Features:
- UNIQUE constraint with partial index prevents double-booking (Layer 3)
- Advisory locks serialize bookings on (doctor_id, appointment_date)
- Redis locks prevent race conditions during slot selection (Layer 1)

TABLE: doctor_schedules
Purpose: Doctor's working hours and availability

Columns:
- id: SERIAL PRIMARY KEY
- doctor_id: INT NOT NULL REFERENCES users(id) ON DELETE CASCADE
- day_of_week: INT NOT NULL (0=Sunday, 1=Monday, ..., 6=Saturday)
- start_time: TIME NOT NULL (e.g., '09:00')
- end_time: TIME NOT NULL (e.g., '17:00')
- is_active: BOOLEAN DEFAULT TRUE
- created_at: TIMESTAMPTZ DEFAULT now()
- updated_at: TIMESTAMPTZ DEFAULT now()

Index:
- (doctor_id, day_of_week)

Relationships:
- many:1 with users

TABLE: schedule_overrides
Purpose: Doctor can block/enable specific dates (vacation, emergency closures)

Columns:
- id: SERIAL PRIMARY KEY
- doctor_id: INT NOT NULL REFERENCES users(id) ON DELETE CASCADE
- override_date: DATE NOT NULL
- is_available: BOOLEAN NOT NULL (FALSE = unavailable, TRUE = available on day off)
- reason: TEXT (e.g., 'Medical emergency', 'Special availability')
- created_at: TIMESTAMPTZ DEFAULT now()

Index:
- (doctor_id, override_date)

Relationships:
- many:1 with users

5.4 MEDICAL RECORDS
-------------------

TABLE: medical_records
Purpose: Patient's uploaded health documents (prescriptions, test reports, etc.)

Columns:
- id: SERIAL PRIMARY KEY
- user_id: INT NOT NULL REFERENCES users(id) ON DELETE CASCADE
- record_type: VARCHAR(50) ('prescription'|'test_report'|'lab_result'|'diagnostic')
- file_url: TEXT NOT NULL (Supabase cloud storage URL)
- file_name: VARCHAR(255)
- upload_date: TIMESTAMPTZ DEFAULT now()
- created_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (user_id) for quick lookup
- (record_type) for filtering

Relationships:
- many:1 with users

5.5 PRESCRIPTIONS
------------------

TABLE: prescriptions
Purpose: Digital prescriptions issued by doctors post-consultation

Columns:
- id: SERIAL PRIMARY KEY
- appointment_id: INT NOT NULL UNIQUE REFERENCES appointments(id) ON DELETE CASCADE
- doctor_id: INT NOT NULL REFERENCES users(id)
- patient_id: INT NOT NULL REFERENCES users(id)
- prescription_details: JSONB NOT NULL
  Structure: {
    medicines: [
      {
        name: string,
        dosage: string (e.g., '500mg'),
        frequency: string (e.g., 'twice daily'),
        duration: string (e.g., '7 days'),
        notes: string
      }
    ],
    notes: string,
    recommendations: string[]
  }
- pdf_url: TEXT (Supabase URL for downloadable PDF)
- status: VARCHAR(50) DEFAULT 'active' ('active'|'expired'|'archived')
- issued_at: TIMESTAMPTZ DEFAULT now()
- expires_at: TIMESTAMPTZ (typically 1 year from issued_at)
- created_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (appointment_id) for 1:1 relationship
- (patient_id, issued_at DESC) for patient's prescription history

Relationships:
- 1:1 with appointments
- many:1 with users (doctor)
- many:1 with users (patient)

5.6 AI PREDICTIONS
-------------------

TABLE: ai_prechecks
Purpose: Symptom prediction results from Clinical BERT model

Columns:
- id: SERIAL PRIMARY KEY
- user_id: INT NOT NULL REFERENCES users(id) ON DELETE CASCADE
- symptoms: TEXT NOT NULL (user's symptom description)
- ai_response: JSONB NOT NULL
  Structure: {
    top_conditions: [
      { disease: string, confidence: float (0-1), description: string }
    ],
    severity: string ('low'|'medium'|'high'|'critical'),
    red_flags: string[],
    recommendations: string[]
  }
- severity: VARCHAR(50) ('low'|'medium'|'high'|'critical')
- created_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (user_id) for patient's history
- (created_at DESC) for recent predictions

Relationships:
- many:1 with users

Special Features:
- CRITICAL severity triggers emergency recommendations
- Red flags detected from symptom analysis
- Severity levels guide appointment urgency

5.7 PHARMACY SYSTEM
--------------------

Purpose: Product categories (Medicines, Supplements, Devices, etc.)

Columns:
- id: SERIAL PRIMARY KEY
- name: VARCHAR(100) UNIQUE NOT NULL
- slug: VARCHAR(120) UNIQUE NOT NULL (URL-friendly: "cold-medicines")

- image_url: TEXT (category icon/image)
- sort_order: INT DEFAULT 0

- created_at: TIMESTAMPTZ DEFAULT now()

- prescription_required: BOOLEAN DEFAULT FALSE
- is_active: BOOLEAN DEFAULT TRUE
- avg_rating: NUMERIC(2,1) DEFAULT 0 (aggregated from reviews)
- review_count: INT DEFAULT 0
- created_at: TIMESTAMPTZ DEFAULT now()
- updated_at: TIMESTAMPTZ DEFAULT now()

Indexes:
- (category_id) for category filtering
- (slug) for lookups
- (sku) for inventory management
- (is_active) partial index where is_active = TRUE
- (avg_rating DESC) for top-rated sorting

Relationships:
- many:1 with pharmacy_categories
- 1:1 with pharmacy_inventory
- 1:many with pharmacy_cart_items
- 1:many with pharmacy_order_items
- 1:many with pharmacy_reviews
- 1:many with pharmacy_wishlist

TABLE: pharmacy_inventory
Purpose: Stock levels and reorder management (1:1 with products)

Columns:
- id: SERIAL PRIMARY KEY

7. REAL-TIME FEATURES & WEBRTC ARCHITECTURE
================================================================================

7.1 WEBRTC PEER-TO-PEER VIDEO SETUP
-----------------------------------

Flow Diagram:
1. Patient & Doctor join same appointment
2. Frontend creates RTCPeerConnection
3. Browsers negotiate SDP offer/answer via Socket.IO
4. Exchange ICE candidates for network traversal
5. Direct P2P connection established (UDP media)
6. Audio/video streams flow peer-to-peer (not through backend)

Socket.IO Signaling Events:

CLIENT EVENTS:
- join-room: { roomId } → Server validates appointment access
- signal: { type: 'offer'|'answer', sdp/candidate } → Relayed to other peer
- mute-state: { isMuted } → Broadcast to peer
- camera-state: { isVideoOff } → Broadcast to peer
- ice-restart-request: {} → Request ICE agent restart
- doctor-end-call: { notes } → Server completes appointment + generates prescription

SERVER EVENTS:
- user-joined / doctor-joined → Ready notification
- signal → SDP offer/answer relayed from peer
- participant-mute-state / participant-camera-state → Peer status change
- call-ended-by-doctor → Call termination notification
- prescription-ready → Download link available
- error → Connection/validation errors

7.2 STATE MACHINE (Call Lifecycle)
----------------------------------

States (stored in Redis):
1. scheduled → Appointment created, waiting for participants
2. waiting → At least one participant in room
3. ongoing → Both participants present (call actively recording)
4. completed → Doctor ended call; appointment marked completed
5. disconnected → Unexpected disconnection (grace period active)

Transitions:
scheduled → waiting (first join)
waiting → ongoing (both participants present)
ongoing → completed (doctor-end-call event)
disconnected (via grace timeout) → timeout recovery within 30 sec

Grace Period:
- When participant disconnects unexpectedly: 30-second grace timeout
- Other participant can reconnect within grace period
- No double-billing or lost session data
- After grace: call marked disconnected, appointment cancelled

7.3 DASHBOARD REAL-TIME UPDATES
--------------------------------

Socket.IO /dashboard namespace:

Doctor Dashboard:
- Subscribes to events on connect
- Receives: student count, active calls, upcoming appointments
- Updates: Every 5-10 seconds via event batching

Admin Dashboard:
- Real-time system stats: total users, revenue, pending orders
- Appointment status changes
- Order notifications

Backend Broadcast:
io.to(`dashboard:doctor:${doctorId}`).emit('stats-update', { ... })

8. BUSINESS LOGIC FLOWS
================================================================================

8.1 APPOINTMENT BOOKING FLOW
----------------------------

Sequence:
1. Patient selects doctor → GET /api/slots (retrieves available slots)
2. Patient clicks slot → POST /api/slots/lock (Redis lock 15min)
3. POST /appointments/book (with lockToken)
   a. Validate 24-hour advance booking window
   b. Verify Redis lock ownership
   c. Acquire PostgreSQL advisory lock (serialize on doctor+date)
   d. Check no existing active appointment for patient
   e. Check slot not already booked
   f. INSERT appointment + room_id (UUID)
   g. COMMIT transaction
   h. DELETE Redis lock
4. Response: { roomId, appointmentId }
5. Patient redirected to waiting room

Error Handling:
- Lock expired: Ask patient to re-select slot
- Slot already taken: Return 409 (conflict)
- Advisory lock timeout: Return 503 (server busy)
- Unique constraint violation: Caught as final fallback

Database Guarantees:
- ACID transactions prevent partial updates
- Advisory lock prevents concurrent bookings on same slot
- Unique index prevents duplicate (doctor_id, date, time, active status)
- Foreign key ensures doctor exists

8.2 VIDEO CONSULTATION FLOW
---------------------------

1. Patient joins call → WS join-room
2. Backend validates: appointment exists, user authorized, time window OK
3. Backend creates call_session record (non-critical failover)
4. Patient sees "Waiting for doctor..."
5. Doctor joins → WS join-room
6. Backend notifies patient "Doctor ready"
7. Browsers exchange SDP offer/answer via Socket.IO
8. ICE candidates exchanged for network connectivity
9. P2P connection established → Audio/video stream flows directly
10. Patient/Doctor toggle mute/camera → Events relayed
11. Doctor talks, takes notes, decides on prescription
12. Doctor clicks "End Call"
13. Backend: endCallWithPrescription()
    a. Save prescription (notes → PDF)
    b. Mark appointment as completed
    c. Save call_session metadata (duration, end_reason)
    d. Transition call state → "completed"
    e. Clean up Redis state
14. Both participants notified: "Prescription ready"
15. Patient downloads prescription as PDF

Call Duration Tracking:
- Starts when both participants join (state → "ongoing")
- Ends when doctor clicks "End Call"
- Stored in database for billing/analytics

8.3 PRESCRIPTION GENERATION FLOW
-------------------------------

Trigger: Doctor ends call

Process:
1. Collect doctor's notes (symptoms, diagnosis, recommendations)
2. Format prescription data (medicines, dosage, frequency, duration)
3. Generate PDF using pdfkit:
   - Header: Doctor name, hospital, date
   - Patient: Name, age, medical history
   - Medicines: Name, dosage, frequency, duration
   - Instructions: Additional notes
   - Footer: Doctor signature (placeholder), license #
4. Upload PDF to Supabase cloud storage (encrypted)
5. Save prescription URL + metadata to database
6. Notify patient: "Prescription ready for download"

PDF Features:
- Professional formatting with boxes/borders
- QR code with prescription ID (for pharmacy verification)
- Prescription token embedded (one-time view link)

8.4 APPOINTMENT CANCELLATION FLOW
----------------------------------

1. User clicks "Cancel Appointment"
2. POST /api/appointments/:id/cancel
3. Backend checks:
   a. Appointment exists & belongs to user (role-based)
   b. Status not 'completed' (can't cancel completed)
   c. Status not 'started' (can't cancel in-progress)
   d. Appointment time > current + 2 hours (cutoff)
4. If time window OK:
   a. UPDATE appointments SET status = 'cancelled', cancelled_by = 'user', cancelled_reason = ?
   b. DELETE any Redis locks for this appointment
   c. Invalidate doctors:available cache
   d. Release inventory if order booked (pharmacy)
5. Response: { success: true }
6. Appointment no longer appears in upcoming

Cutoff Logic:
appointment_datetime - NOW >= 2 hours
Patients can only cancel appointments 2+ hours before scheduled time

Example:
Appointment at 3:00 PM → Can cancel up to 1:00 PM
After 1:00 PM → Cannot cancel (requires doctor approval)

8.5 PHARMACY ORDER FLOW
-----------------------

1. Patient browses products → GET /api/pharmacy/products
2. Add to cart → POST /api/pharmacy/cart/add
3. Update quantity → PUT /api/pharmacy/cart/update (or remove)
4. Checkout → GET /api/pharmacy/checkout page
5. Fill shipping details → POST /api/pharmacy/orders
   a. Lock cart (convert status 'active' → 'converting')
   b. For each item: query inventory, verify stock
   c. Begin transaction
   d. Deduct inventory: stock_quantity -= quantity
   e. Create pharmacy_order with generated order_number (PH-YYYYMMDD-XXXX)
   f. Snapshot each item to pharmacy_order_items (preserves historical pricing)
   g. Calculate subtotal, tax, shipping, total
   h. COMMIT
6. Order created with status = 'pending'
7. Admin review → PUT /api/admin/pharmacy/orders/:id/status (change to 'confirmed')
8. Admin dispatch → status = 'shipped' (with tracking number optional)
9. Delivery → status = 'delivered'
10. Patient can leave review → POST /api/pharmacy/reviews

Stock Validation:
- If stock < quantity during checkout → Return 400 "Out of stock"
- If stock changed after lock → Return 409 "Please retry"

Order Snapshot:
- Preserves product name, price, image at purchase time
- Prevents data inconsistency if product deleted/updated later
- Historical order accuracy maintained

8.6 DOCTOR SCHEDULE MANAGEMENT FLOW
-----------------------------------

1. Doctor views schedule → GET /api/schedule/my
2. Update working hours → PUT /api/schedule/my
   Request:
   [
     { day_of_week: 0, start_time: "09:00", end_time: "17:00", is_active: true },
     { day_of_week: 1, start_time: "09:00", end_time: "14:00", is_active: true },
     ...
   ]
3. Backend:
   a. DELETE existing schedules for doctor
   b. INSERT new schedules
   c. Invalidate doctors:available cache
4. Doctor adds override → POST /api/schedule/override
   Request: { override_date: "2025-03-20", is_available: false, reason: "Medical emergency" }
   a. INSERT schedule_overrides
   b. Cache invalidated
5. Available slot calculation:
   - For each time from 9 AM to 5 PM (15-min intervals)
   - Check if within doctor's working hours for that day
   - Check no appointment booked for that slot
   - Check no override blocking that date
   - Return available slots

9. ERROR HANDLING & LOGGING
================================================================================

9.1 ERROR HANDLING MIDDLEWARE
-----------------------------

Express Error Handler:
```
errorHandler(err, req, res, next)
```

Process:
1. Log error with context (method, path, stack, user_id)
2. Determine if error is operational (handled) or programming error
3. Set HTTP status code:
   - 400: Validation, bad input
   - 401: Authentication required
   - 403: Authorization denied
   - 404: Not found
   - 409: Conflict (double-booking, unique violation)
   - 503: Service unavailable (database down, etc.)
4. Format response:
   - API requests: JSON { message, error, stack (dev only) }
   - Browser requests: JSON with same format
5. Never expose internal details in production (stack traces, query strings)

Error Classification:

Operational (handled):
- Invalid input (validation error)
- Authentication failed (wrong password)
- Authorization denied (role mismatch)
- Resource not found (404)
- Booking conflict (409)

Programming (not handled):
- Null pointer exception
- Type mismatch
- Unhandled promise rejection
- File system error

For programming errors: log, return 500, continue running (don't shutdown)

9.2 LOGGING WITH WINSTON
------------------------

Log Levels:
- error: Critical failures (database down, unhandled exceptions)
- warn: Suspicious activity (auth failures, 400 errors, transient failures)
- info: Normal operations (startup, endpoints hit, successful transactions)
- debug: Development only (query details, variable values)

Log Format:
```
2025-03-20 14:35:22 [INFO] Server running on http://localhost:10000
2025-03-20 14:35:25 [WARN] Socket auth rejected: missing token
2025-03-20 14:35:26 [ERROR] Database pool error: ECONNRESET
```

Logged Events:
- Socket connections/disconnections
- Authentication attempts (success/failure)
- Authorization failures
- API errors (method, path, status)
- Database errors (sanitized)
- File uploads (name, size, mime)
- Appointment bookings
- Prescription generation

Log Storage:
- Console output (all levels)
- File output (logs/ directory, rotated daily)
- Production: Only errors/warnings to file (reduce disk usage)

9.3 APPERROR CLASS
-------------------

Custom error class for operational errors:

```javascript
throw new AppError("Appointment not found", 404);
throw new AppError("Double-booking detected", 409);
```

Properties:
- message: human-readable error message
- statusCode: HTTP status code
- isOperational: true (for distinguishing from programming errors)

Caught by middleware, formatted as JSON, returned to client

9.4 SOCKET.IO ERROR HANDLING
----------------------------

Socket events can fail:
1. Authentication fails → Error event sent, socket not connected
2. Room validation fails → socket.emit('error', { message: '...' })
3. Signaling error → Log and continue (don't crash server)

Graceful degradation:
- If prescription save fails → Still mark appointment completed
- If call_session save fails → Still end call (non-critical)
- If dashboard broadcast fails → Continue (non-critical)

  location /socket.io {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
  }
}

12.3 VERSIONING & RELEASES
--------------------------

Semantic Versioning:
- Format: MAJOR.MINOR.PATCH
- Current: 1.0.0
- MAJOR: Breaking API changes
- MINOR: New features (backward compatible)
- PATCH: Bug fixes

Git Branching:
- main: Production releases only
- develop: Integration branch
- feature/*: Feature development
- hotfix/*: Emergency production fixes

Release Process:
1. Feature complete → Pull request to develop
2. Code review + testing
3. Merge to develop
4. Deploy to staging
5. UAT approval
6. Create release branch (release/v1.1.0)
7. Update version in package.json
8. Merge to main + tag (v1.1.0)
9. Deploy to production

Rollback Procedure:
1. Identify issue in production
2. Create hotfix branch from main: git checkout -b hotfix/issue-name main
3. Fix issue, test locally
4. Create pull request, get approval
5. Merge to main and develop
6. Deploy previous stable version or fixed version
